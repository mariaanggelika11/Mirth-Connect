# Alerting and metrics

GET /metrics requires an authenticated ADMIN (audit:read); the example reverse proxy returns 404 for public /metrics. Scrape on the private engine network with a protected Bearer credential. No payload, channel-name, patient-ID or request-ID metric labels are emitted. SQL gauges reflect retained rows and can decrease after approved retention; process counters/histograms reset on restart.

Implemented gauges: inbound/success/failed/filtered/partial, queue, retry, dead-letter (total and unresolved), oldest pending seconds and circuit open/half-open. Process metrics: inbound attempts/idempotency hits/conflicts, HTTP status groups, processing/destination duration histogram, MLLP active connections/ACK type and script failures. Separate script memory/timeout, pool utilization, per-channel status, login/rate rejection and worker recovery metrics are NOT IMPLEMENTED; use the readiness/log diagnostics until instrumented. Do not mistake aggregate script failures for a specific memory signal.

ALERT_WEBHOOK_URL is optional and must pass the same outbound allowlist/SSRF/TLS checks. Alert body contains only fixed code, severity, FIRING/RECOVERED and timestamp. Initial webhook signals: dead letters, queue age, channel errors and database unavailable. OperationalAlerts stores active/acknowledged/recovered state, pending notification, attempts and successful-send timestamps. Advisory locks and a database cooldown suppress duplicate claims across workers; pending notifications survive process restart. DATABASE_UNAVAILABLE notifications use a bounded per-process fallback because persistence is unavailable during the outage. Successful delivery is audited. Prometheus rules are in deploy/prometheus-alerts.yml; thresholds are starting examples, not hospital SLA commitments.

ADMIN Settings provides an alert inbox and audited acknowledgement. Email, disk-capacity, backup-failure and certificate-expiry signals are NOT IMPLEMENTED. Use a private Alertmanager webhook receiver with owner-approved grouping/repeat intervals for escalation and database-outage grouping. Multi-instance deployments should use a shared Alertmanager for database-outage grouping and escalation. Webhook availability/cooldown/recovery must be exercised in staging.

Dashboard specification: panels for readiness, message outcome gauges, queue/retry/dead-letter depth, oldest pending age, processing and destination duration histograms, HTTP status counts, MLLP ACKs and circuit state. No simulated charts are added to the app.

Dead-letter history is preserved after reconciliation. The alert condition and mirth_dead_letter_open exclude RESOLVED/IGNORED cases, while total dead-letter count continues to show retained evidence. Omitting assignedTo when changing a case preserves its existing operator assignment.
